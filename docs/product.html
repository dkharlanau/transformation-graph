Transformation Graph

Connect fragmented transformation artifacts into one deterministic dependency graph so a team can trace a field, rule, interface, process, test, owner, decision, change, or piece of evidence across the transformation.

The graph is a traceability layer across existing artifacts, not a new master document that asks teams to copy their information again.

Why it exists

Large transformations are documented by domain. Impact questions are cross-domain: “if this field changes, which mappings, interfaces, processes, tests, owners, and release evidence are affected?”

01

Trace across artifacts

Normalize compatible sources into stable nodes and edges instead of manually joining spreadsheets for every question.

02

Make gaps visible

Governance views and scorecards expose missing ownership, test coverage, evidence, systems, and data relationships.

03

Review change semantically

Graph diff and bounded impact traversal turn a changed artifact into a concrete downstream review scope.

One project manifest, many useful views

A governed build composes supported contracts, checks adapter compatibility, reconciles entities, applies policy, and publishes both canonical data and human views.

Build the reference project

transformation-graph build-project \
  examples/project/transformation-project.yaml \
  --output-dir build

transformation-graph impact graph.yaml change.bp-model --depth 2
transformation-graph trace graph.yaml --from-type mapping --to-type field --format markdown

Outputs that travel

Canonical YAML/JSON, build and conformance reports, policy results, scorecards, traceability matrices, role views, GraphML, and a dependency-free static explorer can all come from the same normalized graph.

Not a source-of-truth replacement for process, mapping, or interface contracts. It composes and traces them while preserving their ownership.

Where it connects

This is the graph at the middle of the toolkit: it consumes narrowly owned contracts and feeds broader change and evidence views.

Mapping as Code →Field-level transformation intent becomes graph relationships.Interface as Code →Integration contracts become traceable graph entities.Enterprise Change Graph →Use technical traceability as input to broader enterprise impact.
Agent entry point

Give agents a bounded graph, not a pile of files.

Context packs and MCP reuse the same deterministic graph functions as CLI and CI. Agents can ask for paths, impact, quality, governance, traceability, and role views without inventing connections.

DISCOVER

Manifest + adapter contract

agent-manifest.json describes the safe surface; adapter conformance protects cross-repository semantics.

BOUND

Request local context

Context packs and depth-limited traversal avoid dumping the entire transformation into an agent prompt.

EXPLAIN

Return paths and gaps

Answers should include graph paths, node IDs, governance findings, and evidence rather than unsupported summaries.

Trace the transformation without rebuilding the project in another tool.
